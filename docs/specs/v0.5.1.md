**Versión**: 0.5.1  
**Rama**: `v0.5.1`  
**Tipo**: MINOR — nuevas capacidades retrocompatibles + mejoras de calidad  
**Metodología**: Spec Coding (KIRO) — documentar antes de implementar  
**Fecha de especificación**: 2026-05-14  

---

## 1. Visión

v0.5.0 estableció la base: dark mode, DBML, Minimax, chat mejorado. v0.5.1 afina la experiencia: que la aplicación se sienta pulida, profesional y rápida en cualquier dispositivo, y que la IA genere diagramas con menos fricción y más precisión.

El usuario debe poder trabajar desde un teléfono con la misma confianza que desde un escritorio. La IA debe entender lo que el usuario quiere en el primer intento, sin necesidad de correcciones manuales o reintentos.

## 3. User Stories

### UX

**US-UX-01 — Carga Esqueleto**  
Como usuario, cuando navego entre páginas o cargo datos, quiero ver indicadores visuales de carga (esqueletos) en lugar de texto "Cargando..." o pantallas en blanco, para tener una percepción de velocidad y estructura.

**US-UX-02 — Estados Vacíos Guiados**  
Como usuario nuevo sin proyectos ni diagramas, quiero ver mensajes y acciones sugeridas en los estados vacíos, para saber exactamente qué hacer a continuación.

**US-UX-03 — Consistencia de Confirmación**  
Como usuario, quiero que todos los diálogos de confirmación (eliminar diagrama, eliminar proyecto, cerrar sesión) tengan el mismo estilo y comportamiento.

### Responsividad Móvil

**US-MOB-01 — Editor en Móvil**  
Como usuario en teléfono, quiero editar código de diagrama, ver la previsualización y usar el chat de IA sin que los paneles se solapen o el teclado cubra el contenido.

**US-MOB-02 — Gestos Táctiles**  
Como usuario en tablet o teléfono, quiero hacer zoom con pellizco (pinch-to-zoom) y arrastrar con dos dedos (pan) en la previsualización del diagrama.

**US-MOB-03 — Bottom Sheets**  
Como usuario en móvil, quiero que los paneles flotantes (código, descripción, apariencia) se muestren como bottom sheets deslizables en lugar de overlays de pantalla completa.

**US-MOB-04 — Chat en Móvil**  
Como usuario en teléfono, quiero que el panel de chat se adapte al teclado virtual, manteniendo visible el input mientras escribo.

**US-MOB-05 — Toolbar Adaptativa**  
Como usuario en móvil, quiero que la barra de herramientas del editor colapse en un menú contextual o barra inferior para no saturar la pantalla.

**US-MOB-06 — Sidebar en Modo Presentación**  
Como usuario que entra a modo presentación en el editor, quiero que el sidebar se oculte automáticamente para tener una vista inmersiva del diagrama a pantalla completa, y que se restaure al salir.

### IA Fine-Tuning

**US-AI-01 — Mermaid sin Errores de Sintaxis**  
Como usuario que genera diagramas Mermaid con IA, quiero que el código generado sea sintácticamente válido >90% de las veces en el primer intento, sin errores de `classDef` ni palabras reservadas.

**US-AI-02 — DBML Robusto**  
Como usuario que genera esquemas DBML con IA, quiero que la IA use exclusivamente sintaxis soportada por el renderer (sin `DiagramView`, sin comillas simples, sin `as` alias), produciendo código renderizable en el primer intento.

**US-AI-03 — PlantUML y D2 Consistentes**  
Como usuario de PlantUML o D2, quiero que la IA aproveche skins/themes correctamente y no mezcle sintaxis de otros lenguajes.

**US-AI-04 — Respuestas Streaming**  
Como usuario del chat de IA, quiero ver la respuesta generándose token por token (streaming), para tener feedback inmediato en lugar de esperar segundos sin indicación.

### 4.4 Responsividad — Editor en Móvil

El `DiagramEditorPage` (~3000 líneas) es el componente más complejo. Estrategia:

**Vista móvil (< 768px):**
1. **Vista previa**: ocupa la mayor parte de la pantalla, con controles overlay
2. **Código**: bottom sheet que ocupa 60% de la altura, deslizable
3. **Descripción**: bottom sheet independiente
4. **Chat**: overlay full-screen (ya implementado, verificar teclado)
5. **File browser**: drawer desde la izquierda
6. **Toolbar**: barra inferior fija con iconos (similar a apps móviles)

**Implementación**: crear un wrapper `MobileEditorLayout` que orqueste estas vistas. El layout desktop no se modifica; se selecciona según `window.innerWidth`.

### 4.5 Responsividad — Gestos Táctiles

Modificar el sistema de zoom/pan actual (basado en wheel + mousedown/mousemove) para soportar touch:

```
frontend/src/hooks/useTouchZoomPan.ts
```

- `touchstart` con 1 dedo → iniciar pan
- `touchstart` con 2 dedos → iniciar pinch zoom
- `touchmove` → calcular delta de distancia para zoom, delta de posición para pan
- Prevenir scroll de página durante interacción con el diagrama

### 4.6 Responsividad — Teclado Móvil en Chat

Problema actual: en móvil, al abrir el teclado en el chat, el panel no se ajusta y el input queda oculto.

Solución:
- Usar `visualViewport` API para detectar cuando el teclado está abierto
- Ajustar `height` del panel de chat basado en `window.visualViewport.height`
- Hacer scroll al último mensaje cuando cambia el viewport

### 4.7 Responsividad — Sidebar en Modo Presentación

Actualmente, al activar `isFullscreen` en el editor, el sidebar permanece visible (160px o 64px colapsado), restando espacio a la vista inmersiva.

**Solución:**
- `DiagramEditorPage` expone el estado `isFullscreen` vía contexto o callback
- `SidebarLayout` reacciona a `isFullscreen`: cuando es `true`, aplica `margin-left: 0` y oculta el sidebar físico con `display: none`
- Al salir de presentación (`Escape` o botón), el sidebar se restaura a su estado previo (colapsado o expandido)
- En móvil, el sidebar ya es overlay — no aplica este cambio

**Archivos involucrados:**
- `frontend/src/components/SidebarLayout.tsx` — recibir prop `isPresentationMode` o leer de contexto
- `frontend/src/pages/DiagramEditorPage.tsx` — comunicar `isFullscreen` al layout
- `frontend/src/components/Sidebar.tsx` — opcional: transición suave al desaparecer

**Implementación mínima**: `SidebarLayout` acepta prop opcional `hideSidebar: boolean`. Cuando es `true`, `margin-left: 0` y el sidebar recibe clase `hidden`. El `DiagramEditorPage` pasa `hideSidebar={isFullscreen}`.

### 4.8 IA — Respuestas Streaming (SSE)

Implementar Server-Sent Events en el backend para el chat:

**Backend:**
- Nuevo endpoint: `POST /api/v1/chat-sessions/{id}/stream`
- Streaming via `StreamingResponse` de FastAPI
- Cada chunk se envía como evento SSE: `data: {"type": "text"|"code"|"done"|"error", "content": "..."}`
- Soporte por proveedor:
  - OpenAI: `stream=True` nativo ✓
  - DeepSeek: `stream=True` (compatible con API OpenAI) ✓
  - Gemini: `generate_content(stream=True)` ✓
  - Claude: streaming messages API ✓
  - Minimax: streaming vía SSE nativo ✓

**Frontend:**
- Modificar `apiService.sendChatMessage` para aceptar callback `onChunk`
- `AIChatPanel` muestra texto incremental con cursor parpadeante
- El código de diagrama aparece en un bloque diferenciado
- Al recibir `done`, se parsea el código y se muestra la previsualización

### 4.9 IA — Mejora de Prompts por Tipo

**Mermaid:**
- Agregar 3 ejemplos few-shot completos en `get_mermaid_context()`:
  1. Diagrama de flujo con estilos y subgrafos (ejemplo correcto)
  2. Diagrama de secuencia (ejemplo correcto)
  3. ERRATA: mostrar código incorrecto → versión corregida (enseña a evitar errores)
- Reforzar lista de palabras reservadas con ejemplos de error
- Agregar validación pre-envío: el system prompt incluye "ANTES de responder, verifica mentalmente que: (1) no usas classDef con nombres reservados, (2) class solo referencia IDs de nodos sin comillas, (3) classDef va después de todas las conexiones"

**PlantUML:**
- Agregar 2 ejemplos few-shot con skinparam
- Regla explícita: "NUNCA generes más de UN diagrama (un solo @startuml...@enduml)"
- Advertencia sobre secuencias multi-participante con activate/deactivate balanceado

**D2:**
- Agregar 2 ejemplos few-shot con temas y estilos
- Lista exhaustiva de propiedades de estilo válidas (las del contexto Kroki)
- Regla: "style.dash NO existe, usa style.stroke-dash: 5"

**DBML:**
- Agregar 3 ejemplos few-shot:
  1. Esquema simple (users + posts)
  2. Esquema con Enums e indexes
  3. ERRATA: código inválido → versión corregida
- Reglas reforzadas:
  - "NUNCA uses comillas simples (') — SIEMPRE comillas dobles (\")"
  - "NUNCA uses DiagramView, Schemas, Project — solo Table, Enum, Ref, Note, TableGroup, indexes"
  - "NUNCA uses alias con 'as' en nombres de tabla"
  - "Cada Table, Enum, e indexes requiere llaves { }"

### 4.10 IA — Mejora de Extracción de Código

El sistema actual tiene 5 fallbacks de extracción en `send_message()`. Mejoras:

1. **Unificar la lógica** en una función `extract_diagram_code(ai_text, diagram_type)` reutilizable
2. **Agregar fallback por tipo**: cada tipo de diagrama tiene marcadores naturales:
   - Mermaid: regex de tipos (`graph TD`, `sequenceDiagram`, etc.)
   - PlantUML: `@startuml...@enduml`
   - D2: patrones de declaración (`nombre: {`)
   - DBML: `Table nombre {`
3. **Puntuar candidatos**: cuando hay múltiples candidatos de código, elegir el más largo (probablemente el más completo)
4. **Logging**: registrar qué fallback se usó para cada extracción (métricas de calidad)

## 6. Criterios de Aceptación

### UX

- [ ] Los esqueletos de carga aparecen en <200ms tras navegación
- [ ] Estados vacíos muestran una acción clara (botón CTA)
- [ ] Todos los diálogos de "¿Estás seguro?" usan el mismo componente

### Responsividad

- [ ] Editor usable en viewport 375x667 (iPhone SE) sin scroll horizontal
- [ ] Zoom con pellizco funciona en previsualización de diagrama
- [ ] Bottom sheets se abren/cierran con gesture swipe
- [ ] Teclado móvil no oculta el input del chat
- [ ] Tooltips no aparecen en dispositivos táctiles
- [ ] Modal de exportación es scrolleable en móvil
- [ ] Sidebar se oculta al entrar a modo presentación y se restaura al salir

### IA

- [ ] Mermaid generado por IA: >90% de tasa de primer intento sin errores en 50 pruebas
- [ ] DBML generado por IA: >80% de tasa de primer intento sin errores en 50 pruebas
- [ ] Streaming muestra primera palabra en <500ms tras enviar mensaje
- [ ] Extractores de código cubiertos con tests unitarios (≥90% coverage)

## 7. Riesgos y Mitigaciones

| Riesgo | Impacto | Mitigación |
|--------|---------|------------|
| Streaming incompatible con algún proveedor | Medio | Implementar fallback a non-streaming si el proveedor no soporta |
| Cambios en prompts empeoran generaciones | Alto | Hacer A/B manual: correr 20 generaciones con prompt antiguo vs nuevo antes de mergear |
| Complejidad del MobileEditorLayout | Medio | Mantener desktop intocado, feature-flag `useMobileLayout` |
| Tests E2E frágiles | Medio | Usar data-testid, no selectores CSS; grabar videos en CI |
| Regresiones en editor desktop por cambios móviles | Alto | El layout móvil es un componente wrapper separado, no modifica el desktop |

## 8. Definición de Done

Una tarea está completa cuando:

1. Código implementado con type hints (Python) / tipos (TypeScript)
2. Tests unitarios pasando para la funcionalidad nueva
3. Sin regresiones en tests existentes
4. i18n: claves agregadas a `es.json` y `en.json` (si aplica)
5. Probado manualmente en viewport desktop + móvil
6. Documentado en CHANGELOG (entrada concisa)
